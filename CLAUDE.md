# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`snap-carousel.js` is a zero-dependency `<snap-carousel>` custom element built on CSS scroll-snap. Plain JavaScript (ES2022, native private fields), hand-written `.d.ts` files, built with Vite.

Two constraints drive most design decisions:

- **Bytes matter.** The core is ~4.6 kB gzipped and a carousel must never download code for a feature it doesn't use. Check `npm run size` output after any change to `src/`.
- **Configuration is HTML attributes only.** Users set options through CMS UIs, so nothing may require them to write CSS or JS to configure a carousel. CSS is for visual styling only.

## Commands

```bash
npm run dev          # Vite dev server on the demo page (src/index.html), which imports src/snap-carousel.js directly
npm run build        # build:lib, then the demo site into docs/
npm run build:lib    # library into dist/ (vite --mode library), copy types, print sizes
npm run size         # minified + gzipped size of every file in dist/
```

There are no tests and no linter (`npm test` is a no-op that exits 0). Verify changes in the browser with `npm run dev`. Native controls only exist in Chrome/Edge 135+, so check both a Chromium browser and Firefox or Safari when touching controls, nav or layout.

Use Node 18+ (`engines`, and required by Vite 5). `.nvmrc` still says v16 and is stale.

## Build outputs are committed

`dist/` (the npm package) and `docs/` (the GitHub Pages demo site) are both tracked in git and both are emptied and regenerated by `npm run build`. Don't edit them by hand; rebuild and commit the result with the source change.

`vite.config.js` has two modes:

- `--mode library`: one entry per public import path (`snap-carousel`, `base`, `features/controls`, `features/nav`, `features/pager`), ES format only, minified by terser. These map to the `exports` in `package.json`; adding a feature means adding an entry here, in `exports` (already a `./features/*` wildcard), and a `.d.ts`.
- default: builds `src/index.html` into `docs/`.

Types are not generated. `src/types/**/*.d.ts` are maintained by hand and copied to `dist/types/` by `build:types`, so any change to a public API, option, state field or hook must be mirrored there manually.

## Architecture

### Core and features

`src/base-carousel.js` holds `BaseCarousel`, which does everything that isn't a UI control: config parsing, responsive breakpoints, page computation, scroll tracking, autoplay, sync, ARIA. It has no side effects on import and registers nothing.

Features (`src/features/*.js`) are plain functions `carousel => void` that call `carousel.registerHook(type, callback)`. They only use the public surface of the base class (`settings`, `state`, `elements`, `states`, `getSlotElements()`, `goTo()`, `isLtr()`), since everything else is in `#private` fields. Each feature file exports two forms of the same thing:

- the plugin function (`controls`, `nav`, `pager`), attached at runtime with `carousel.use(feature)`
- a class mixin (`ControlsFeature`, …) for static composition with `createCarousel(...mixins)`

Hooks, in order:

- `setup`: attributes were (re)read, before the active breakpoint is resolved
- `init`: pages were recomputed. Runs on first connection, when the matching breakpoint changes, and when the scroller's children change. Features rebuild their DOM here, so `init` callbacks must be idempotent.
- `updateState`: the current page index changed

`use()` runs the new feature's `init` callbacks immediately if the carousel is already ready, which is what makes late, lazy loading work.

### SnapCarousel: choosing native or JS per carousel

`src/snap-carousel.js` is the side-effectful main entry: it defines `SnapCarousel` and registers `<snap-carousel>`. Its `init` hook (`#chooseFeatures`, registered first so it runs before any feature) decides, for `controls` and `nav`, between:

- **Native**: the browser draws them with `::scroll-button()` / `::scroll-marker`. No JS is loaded. Signalled by custom states `native-controls` / `native-nav` on the host, which `src/style.css` matches with `:state()`. The option is then forced to `false` in `settings.current` so an already-loaded JS feature stays hidden.
- **JS**: the feature is fetched with a dynamic `import()` and attached with `use()`.

Native is used only when `CSS.supports('scroll-marker-group: after')`, the user slotted nothing into the feature's custom slots, and (for controls) there's no `loop` and `perPage >= floor(displayed)`. The pager is always JS. This decision is re-made on every `init`, so it can differ per breakpoint.

Consequence: any change to the look, content, order or labelling of buttons and dots has to be made twice, in the JS feature + `template.html` + `host.css`, and in the native rules in `style.css`, and the two must stay visually and behaviourally equivalent. The README's "Native buttons and dots" section documents this contract for users; `src/main.scss` (demo page styles) shows the mixin pattern for styling both.

### Two stylesheets, two scopes

- `src/host.css` is adopted into each shadow root: host grid layout, `::slotted()` scroller rules, placement of the shadow parts.
- `src/style.css` is adopted once into the **document** (`document.adoptedStyleSheets`), because it targets things shadow CSS can't reach: the slides (children of the slotted scroller) and the native pseudo-elements. It selects through markers the JS sets on light DOM: the `snpc-s` attribute on the scroller, `data-index` on slides, and the `sc-anchor` / `sc-anchor-stop` / `sc-page` classes. Native rules are wrapped in `:where()` so page styles always win.

Both are imported with `?inline`, and `template.html` with `?raw` (whitespace stripped by a small plugin in `vite.config.js`). The library ships no visual styles for buttons and dots, only layout.

### Configuration flow

`defaultConfig` is the single source of options; `observedAttributes` is derived from it (kebab-case, plus `data-` prefixed variants, plus a JSON `options` attribute that replaces individual attributes). Adding an option means adding it there, to `CarouselOptions` in `src/types/base-carousel.d.ts`, and to the README table.

`settings` has three layers: `default` → `origin` (defaults + attributes) → `current` (origin + the widest matching `responsive` entry, tracked with `matchMedia` listeners). Always read `settings.current`. Attribute values go through `JSON.parse` with a string fallback, and an empty attribute means `true`.

Sizing reaches CSS as custom properties set on the host (`--perpage`, `--gap`, `--padding`, `--behavior`, `--prev-label`, `--next-label`).

### Scroll and state

Position is always derived from `getBoundingClientRect()` relative to the scroller and its scroll-padding, never from `scrollLeft` sign, so RTL and vertical work without special cases. Keep it that way.

`goTo()` updates the index and UI up front, then sets `#preventUiUpdate` so the intermediate pages crossed during the smooth scroll don't flicker the controls; `scrollend` clears it. `scrollend` is polyfilled by a dynamic import of `scrollyfills` only in browsers lacking it (the one runtime chunk in `dist/chunks/`).

The element dispatches `scrollstart`, `scrollupdate` and `scrollend` CustomEvents with the state as `detail`.

## Conventions

- Commits follow Conventional Commits; `CHANGELOG.md` and the `chore(release): x.y.z` commits are generated by standard-version. Don't edit the changelog by hand except to add notes a release needs.
- Work happens on `develop`; `main` is the release branch. Creating a GitHub release triggers `.github/workflows/npm-publish.yml`, which publishes to npm (`prepublishOnly` rebuilds).
- User-visible behaviour changes belong in the README, including the "Migrating from 1.x" list for anything breaking, and usually in a demo on `src/index.html`.
- 2-space indentation, 4 for JSON (`.editorconfig`).
